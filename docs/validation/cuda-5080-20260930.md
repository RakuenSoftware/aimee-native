# RTX 5080 execution validation — 30 September 2026

The published portable 0.2.0 wheel passed numerical, memory-activation and live
Gemma4 12B checks on an NVIDIA RTX 5080. This run uses
an isolated host environment with upstream vLLM 0.30.0, PyTorch 2.13.0+cu130,
Triton 3.7.1 and Python 3.12.14. The NVIDIA driver is 615.71.09 and the GPU has
16,303 MiB of memory (SM 12.0). The existing research environment is unchanged.

The wheel SHA-256 is
`511a16373291774b85d427468f484fedc531310465c25ee55d22fa79ec99ce37`.
All 21 installed plugin files match the published wheel byte-for-byte, including
the Rust library previously executed on AMD. No CUDA-specific Aimee rebuild,
vLLM fork, model encoder or optional GGUF binary is introduced. The GGUF extra
uses the same upstream Triton implementation packaged with 0.2.0.

## Numerical execution

The existing portable GPU test executed on the 5080. All decoder cases passed
bit-for-bit, covering all 65,536 BF16 patterns, escape values, odd lengths and
partial blocks. Rust runtime warm-up through the public PyTorch bridge passed.

Native attention passed the existing independent PyTorch reference comparison
for ragged prefill/decode, grouped heads, paged text storage, multiple native
banks, sliding windows, fully excluded memory and soft caps. Maximum absolute
error was 0.0009765625, within the unchanged test tolerance (`atol=0.016`,
`rtol=0.02`). Floating-point attention output is compared numerically; lossless
memory decoding and activation are compared bit-for-bit.

## Memory activation and ownership

The activation test now accepts requested tensor-parallel layouts and maps their
shards onto available devices. This allows checking complete banks and both
halves of a two-rank layout sequentially on a single GPU. It does not simulate
or validate communication between two NVIDIA GPUs.

Six prepared publications from public/synthetic fixtures were checked with world sizes 1 and 2,
raw and lossless transport, and three activations per case. Every activation
released its Rust handle, evicted residency and forced garbage collection before
comparison against Rust's raw-storage reference. Two fresh-process suites passed
all **216 activations** (36 cases × 3 activations × 2 suites).

## Live-model protocol

The live probe uses the installed `aimee-native connect` and `serve` commands,
mutual TLS and the existing authorized Aimee test identity. It asks twice for
three canary facts absent from the prompt. The consumer must be loaded from the
installed wheel. This is an integration check, not a new learning benchmark.

Gemma4 12B uses the same 12,863,382,944-byte GGUF weight file as the AMD check,
with one GPU, a 2,048-token model limit, one active sequence, 128-token prefill
batches and 92% GPU-memory utilization. The larger Q8 model profiles used on the
two XTXs exceed this card's VRAM; this run does not establish their execution on
a single 5080.

## Live result

Both requests passed, returning all three native facts. Each used **27 prompt
and 39 completion tokens**. Complete response times were **7.92 seconds** and
**2.91 seconds**. These times include inference and any request-time compilation;
they are not memory-application latency measurements. Different runtime versions,
GPU counts and serving settings prevent treating the earlier AMD response times
as a matched speed comparison.

The successful pip-only runtime uses the upstream setting:

```sh
export VLLM_USE_FLASHINFER_SAMPLER=0
```

This selects vLLM's PyTorch sampler. Its optional FlashInfer sampler attempted
JIT compilation during startup and failed to locate `nvcc`. Selecting the
supported sampler avoids that requirement for this configuration; it changes
neither the Aimee attention kernel nor the memory path. No upstream source files
were modified. The installed plugin and its Rust library remain byte-identical
to the AMD-tested release.

## Test setup corrections

The initial live probe failed before inference because the copied connection
configuration still referenced the container's client-certificate path. Copying
the certificate into the isolated private client directory fixed authenticated
connection. No credential contents are archived.

The next startup failed when the host launcher canonicalized a model path under
`/proc/<container-pid>/root`: the result referred to a container-internal path
absent on the host. The model files were copied into the isolated host directory
for a normal local path. These setup failures did not require changing the
published plugin. The initial environment setup also installed the GGUF wheel
with dependency resolution disabled; normal resolution then installed its
required `gguf==0.19.0` parser. These failures and the FlashInfer startup failure
are retained separately from final results. The allocator emitted retry warnings
during weight loading but completed loading at 12.33 GiB; the final serving run
completed both requests.

The probe stopped its server after the two requests. The final GPU check found
no compute processes, 4 MiB used and 0% utilization. The separate 5080 research
environment was not modified.

## Coverage boundary

These checks provide physical CUDA execution evidence for the RTX 5080, beyond
the earlier offline SM 12.0 compilation. They do not certify every NVIDIA GPU,
Intel XPU, multiple NVIDIA GPUs, or every model and quantization. Earlier AMD
results and offline compilation targets remain recorded in the
[portable release report](portable-plugin-20260930.md).
