# RTX 5080 expanded serving checks — 30 September 2026

This follows [the numerical and activation validation](cuda-5080-20260930.md)
using the **unchanged published 0.2.0 wheel**, the same Gemma4 12B Q8_0 model,
upstream vLLM 0.30.0 and single RTX 5080. No production implementation change
is made in this campaign. Test source and raw results belong in aimee-qwen.

## Protocol

1. Reconnect the installed client to live Aimee over authenticated TLS, repeat
   the three-fact canary query 24 times, interrupt a streaming native request,
   and require an automatically restarted model process to answer correctly.
2. Start an isolated server with an **empty native catalogue and no selection
   socket**. Alternate 24 no-memory and 24 text-memory queries. This makes the
   absence of native memory explicit; merely omitting `vllm_xargs` from an
   ordinary live-Aimee request does not disable automatic selection.
3. Start a separate server with one frozen canary publication. Across 24 rounds,
   alternate explicit native selection, no selection, the same facts as prompt
   text, and unrelated integer addition. This checks request isolation while
   native state is resident. It is a controlled consumer experiment, **not a
   substitute for live authorization testing**.

The question requests vault code, project and drink. Correct recall requires
all three of `28461`, `Juniper`, and `Hibiscus`. Text controls supply those same
facts in a concise sentence; they do not claim byte-identical source formatting
or encoder input. Arithmetic expects only the exact integer. Generation uses
zero temperature, a 100-token output limit and disabled thinking. The configured
context limit is 2,048 tokens, one scheduled sequence, and 128 batched tokens.

These are repeated reliability checks on one three-fact canary, not independent
knowledge examples, a broad accuracy benchmark or a learning experiment.
Whole-response times include generation and are not memory-application timings.
Arms run in fixed order, without randomized crossover. Requests are sequential;
this is not a concurrent or multi-tenant isolation validation.

## Live Aimee results

All **24/24** repeated native requests returned all three facts. Each request
used **27 prompt tokens and 39 completion tokens**, with no memory facts in the
prompt. The interrupted-stream check also passed: the supervisor replaced its
owned model process and the next authorized request returned all three facts.
The measured interval from interruption through the recovered answer was
**75.295 seconds**, including complete model restart and generation.

This is graceful recovery through process replacement, not uninterrupted
availability or request resumption. Requests arriving during restart can fail.

## Empty-catalogue controls

| Condition | All three facts correct | Prompt tokens | Completion tokens |
|---|---:|---:|---:|
| No memory | 0/24 | 27 | 83 |
| Text memory | 24/24 | 49 | 39 |
| Live native memory, preceding run | 24/24 | 27 | 39 |

For this concise text baseline, native delivery avoids **22 prompt tokens per
request (44.9% of the text condition's full prompt)**. Total generated-request
usage is 66 tokens for native versus 88 for text, a 25% reduction with equal
39-token completion lengths. These percentages describe this canary only. The
native bank still occupies storage and device memory and participates in
attention; prompt-token savings do not mean zero memory or compute cost.

Whole-response median latency is 2.966 seconds for live native, 2.765 seconds
for text, and 5.859 seconds for no memory. Live native includes authorization
and selection; the isolated text control does not. No-memory also generates a
longer answer. These timings do not establish a native speed advantage or
measure memory application in isolation.

## Frozen-bank request isolation

All **96/96** requests completed without an HTTP or runtime error:

| Condition | Result | Median full-response time |
|---|---:|---:|
| Native selection | 24/24 recalled all three facts | 2.769 s |
| No selection, bank resident | 0/24 recalled the canary facts | 5.858 s |
| Text memory, no native selection | 24/24 recalled all three facts | 2.770 s |
| Arithmetic, no native selection | 24/24 exact answers | 0.215 s |

Native and text have the same 39-token completion length and essentially equal
full-response medians here. The roughly one-millisecond difference between
medians is not evidence of a speed advantage. The prompt counts remain 27 for
native and 49 for text. Native facts were not observed in unselected replies;
this supports sequential request isolation for this bank and configuration.

Across the completed live, empty-catalogue and mixed runs there are **169 scored
answers**, including the post-restart answer: 49 native recall, 48 text recall,
48 no-memory recall and 24 arithmetic. The interrupted stream is a separate
lifecycle exercise, not another scored answer. These counts exclude the retained
initial failed run and must not be described as 169 distinct knowledge tasks.

## Problems discovered

The first live test obtained the correct native answer, then the interleaved
arithmetic request received HTTP 503. A direct authenticated request to Aimee's
`/v1/native/select` returned `native publication unavailable` for that same
arithmetic query, before model generation. This is an end-to-end selection-path
limitation, not evidence of a CUDA attention failure. The test was preserved;
the subsequent live run tests supported canary requests, while the frozen-bank
run separately measures consumer behavior on unrelated requests.

The present publication protocol requires a nonempty record selection and a
prepared publication. It does not distinguish an authorized **no relevant
memory** result from unavailability. General-purpose serving needs an explicit,
authority-approved no-memory outcome, propagated through the broker and worker
without reusing a previous request's memory. Errors or authorization failures
must continue to fail closed. Returning no memory for every 503 would hide
outages and is not an acceptable fix.

The initial control launcher also failed before loading the model because the
compiled CLI module has no code object for `python -m`. Calling its exported
`main()` function fixes that harness issue without changing the installed wheel.
Both original failures are retained with the campaign evidence.

## Reproduction and evidence

The installed-client test is
[`standalone_plugin_probe.py`](../../distribution/tests/standalone_plugin_probe.py),
run with `--repeat 24 --interrupt-and-recover`. Its initial run additionally
used `--interleave-controls` and exposed the no-match limitation above.
[`standalone_memory_controls.py`](../../distribution/tests/standalone_memory_controls.py)
runs the empty-catalogue control by default and the controlled mixed protocol
with `--include-native`. The exact executed script snapshots, raw JSON answers,
compressed logs, initial failures and checksums are in
[`artifacts/cuda-5080-expanded-20260930/`](artifacts/cuda-5080-expanded-20260930/).
Credentials, client configuration and memory payloads are excluded.

After completion, the common GPU reservation was released and `nvidia-smi`
reported no compute processes, 4 MiB used and 0% utilization. No other service
or research environment was stopped or modified.

The live no-match limitation recorded above was subsequently fixed and validated
in [plugin 0.2.1](authorized-empty-20260930.md). Original results remain unchanged.
