PRIVATE RESEARCH — native tool use through Aimee

Conclusion

Native tooling is viable as a bounded mechanism. Stock Gemma4 E2B on CPU can
consume task/capability information natively, express a semantic need, receive
an owner-resolved tool result through native memory, and use the new evidence.
No tool-specific training was required. This is sufficient direction for future
integration; general autonomous routing reliability is a later milestone.

Strongest direct observation

The private plugin prototype held a completed model contribution containing a
request for measured throughput. Aimee's real core interpreter/compiler selected
a privately bound lookup, and a synthetic owner fixture read52MB/s. The plugin
accepted owner-distributed revision001 after999, injected the updated publication,
and started a new inference segment. E2B revised 'can likely sustain70MB/s' to
'not currently sustaining'70MB/s, explicitly citing52MB/s.

The model then requested installation date. At the configured two-contribution
budget the owner fixture ended with clarify; the second lookup was not executed.
This was a demonstrated request/evidence loop, not an autonomous completed report.
Both owner sessions closed, worker pins released, and owned services stopped.

Other supporting results

- E2B typed proposals:16/16 valid interpretation/compilation;12/16 met task
  requirements. Successful compilation is not proof of a correct proposal.
- Lifecycle:48/48 selected-fact checks per tested E2B/Qwen model, including
  owner-driven publication changes and withdrawal controls.
- Longer-conversation checks:72/72 per model across three arms;24/24 native vs
  current-prefix exact token pairs. History comparisons also change retained
  state, so they do not establish a pure context/computation reduction.
- Plugin protocol/lifecycle:11 tests pass, including binding, stale replies,
  opaque revisions, concurrency serialization, UNIX framing, budgets, deadline,
  cancellation, repeated cancellation and failed-cleanup refusal.
- Broader autonomous discovery was uneven. Mixed needs and authored assessments
  sometimes resolved, sometimes failed. These limits are preserved in raw data.

Architecture supported by the results

The native LLM plugin hosts publication consumption, request-bound contribution
transport and the inference lifecycle. Aimee owns semantic interpretation,
conflicts, private tool/resource bindings, authorization, resolved revisions,
update distribution, OS-specific execution details and observed effects.
The adapter trusts the owner-selected resolved view rather than ranking revisions.

Start with completion-boundary handoff. The prototype does not infer semantic
intent directly from intermediate tensors and does not resume one suspended
decoder sequence. Native updated state enters a fresh inference segment. The
component is callable from the local plugin package; automatic ordinary serving
interception and the enrolled owner channel are not yet integrated.

Qualification limits

The new loop exercised real CPU native vLLM and real core interpretation, with
synthetic identities and fixture execution. Full authenticated enrollment,
source/memory authorization and physical canonical dispatch remain unqualified
through that loop. Reasoning adaptation/weight plasticity was not tested.

Capability information and evidence were outside the task model's ordinary
prompt. Native preparations and owner interpretation have separate costs.
The latest run had84 ordinary task-input tokens,512 task-output tokens,74/104/122
native preparation-prefix tokens, and two owner semantic calls totaling1223
input and152 output tokens. No system-wide context multiplier or compute saving
is established.

Next integration boundary

Wire the plugin loop to the enrolled Aimee owner channel and serving entrypoint,
with per-request native selection replacing the fixture's serialized global lane.
Keep further code, experiments and results in this private aimee-qwen repository.
