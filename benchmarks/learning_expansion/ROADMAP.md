# Expansion roadmap: native consumption and governed self-learning

Date: 11 October 2026. Starting manuscript: unified review PR 35. This is an
execution plan, not new scientific evidence or a change to that paper's claims.

## Two goals and the evidence required

1. Reuse selected native knowledge only when needed, without retaining record
   text in later conversation. Quantify context, computation, state and cost.
2. Improve frozen receivers through retained experience, then measure capability
   per cost across receiver sizes. Expand the existing acquisition, failure
   recall, shared-learning and production learning-loop results.

Neither a tenfold carried-context reduction nor a small-model/large-model
crossover is a promised outcome. Native banks still consume positions and
attention work while attached. A model-request boundary is not yet proof of
within-generation hotplug. Store ownership, model-directed selection, native
consumption and the learning policy are distinct interfaces.

## Phase 1: scope and context cost

Current runnable design is in README.md. Report curves by turn, record size,
value position and actual history length, not a pooled universal percentage.
Show persistent, removed and native arms together. Charge preparation once per
record, attachment each selected turn, generation, cleanup and history bootstrap
separately. Keep scoped history caching enabled in both scoped arms. Measure
retained public text, exact task/input tokens, actual checkpoint bytes, causal
key-query counts and latency. Byte-time proxies and GPU sampled energy must be
labelled as such; later allocator/event instrumentation can refine them.

The analytic full-attention prefill count for Q new tokens and H existing keys
is layers × [Q H + Q(Q+1)/2]. Decode with D tokens adds layers × [D(H+Q) +
D(D+1)/2]. Validate every phase against emitted counters. K/V bytes per token
are 2 × layers × KV heads × head dimension × element bytes. Native does not
eliminate this state; the advantage under test is reuse and request lifetime.

The current size sweep uses synthetic padding to separate payload size from
semantic complexity. Add dense paragraphs in the external benchmark. Arithmetic
probes improve on a constant-color instruction but do not establish resistance
to general reasoning distraction. A separate saturation panel must record
whether the boundary is the position limit, allocation failure or serving policy.

## Phase 2: model-directed access and delivery

Use MuSiQue supporting paragraphs as a first external multi-hop workload; retain
its official answer/support scoring and shared-passage clusters. Its maintainers
warn about overlap with seed datasets; preserve source IDs and avoid training
leakage. Primary source: https://github.com/StonyBrookNLP/musique .

Freeze the earlier A–F specification from its original proposal before claiming
an exact replication. The invariant design is identical request schema and
allowed record IDs, crossed with forced requests (delivery only) and free
model requests (selection plus delivery). Compare in-process text, actual MCP
text and native continuation at the request boundary; include disabled and
oracle-selected quality references. Retain persistent versus removed scope as
explicit policy factors. Prefix caching is a secondary text execution setting,
not a substitute for the persistent-context comparison.

Pilot first, then target >=1,000 distinct tasks per prespecified request-count
stratum (1, 2 and 4 requests) where the dataset supports it. Prespecify a 2 pp
accuracy non-inferiority margin and cluster by task/shared source paragraphs.
Report paired discordances and clustered intervals. McNemar describes paired
outcomes on distinct tasks; never use repeated identical greedy runs as extra
independent observations. Report request validity, record-selection recall,
unsupported requests, retries, bytes crossing the interface and end-to-end cost.

## Phase 3: expand deployment-outcome self-learning

Pilot about 30 issue instances from a pinned fresh benchmark snapshot, with
creation dates after each evaluated checkpoint's documented cutoff where that
can be established. SWE-bench-Live is a candidate maintained source, not automatic
proof that every item is post-release: https://github.com/microsoft/SWE-bench-Live .
Pin individual issue, repository and snapshot identities before any model sees them.

Temporal within-repository splits are primary; held-out repositories are
secondary. Acquire candidate procedures only from training trajectories,
existing visible tests, agent-written reproduction scripts, builds or explicit
user corrections. Candidate validation cannot inspect hidden evaluation tests,
reference patches or expected hidden answers. Store those grading resources in
a separate evaluator inaccessible to the agent, credentials and container.
Log artifact manifests, mounts and access events. Scan admitted text for issue
IDs, copied fixes and held-out material; human review can audit admission errors
but cannot secretly improve the automatic validation policy.

Specify the learning algorithm as observe → propose → validate → consolidate /
deduplicate → conflict resolution → admit → revise/withdraw. Preserve rejected
candidates and failure signals. The harness grant boundary is invariant; no
learned record grants authority. Freeze three stream orders before the pilot's
held-out outcomes. Measure accepted and bad-admission rates, per-procedure
execution, corrections, negative transfer and earlier held-out performance.

Controls: no memory, budget-matched static memory and adaptive learning. Evaluate
frozen snapshots under none, fresh removed text, text with ordinary history
prefix caching enabled, and native delivery. Persistent context is an additional
scope control. Use one online end-to-end learning run after snapshot evaluation
isolates acquisition from delivery. Report empty/static/on comparisons without
pooling copied fixture repeats. Give training/acquisition/evaluation budgets and
charge failed proposals and rejected attempts.

Use the same selection/delivery loop with the Aimee store and one backend chosen
after a capability/API audit (Mem0, Cognee or Hillock). Pin versions, record
schema, authorization/revision semantics and retention budget; do not pretend
unsupported guarantees are identical. Core learning signals, candidate policy
and consumer configuration remain fixed when measuring backend effects. Add a
non-coding stream and donor-to-other-receiver transfer after the repair pilot.

Deliberately bad records belong in an isolated synthetic admission test, never
production memory. Evaluate detection, harm to prior tasks and recovery after
correction. Learning quality and grant enforcement are different outcomes.

## Phase 4: expand capability per cost

Reuse the exact task sets, memory snapshots and budget from Phase 3. Start with
fully resident small checkpoints on the 5080; add ~4B, ~12B and a 27–32B reference
when an appropriate all-resident profile is available. Compare no memory, scoped
text and native learned memory. Match task budgets, decoding, exposure and
precision as far as possible; disclose unmatched quantization and hardware.

Measure task success, tokens/s, synchronized end-to-end latency, peak active and
reserved VRAM, acquisition cost, GPU sampled energy (with idle baseline and
sampling error) and cost under a disclosed hardware/amortization model. Avoid
fabricated electricity tariffs or dollar costs. Plot task success against tasks
seen, with the large no-memory control and confidence bands; report a crossover
only when measured. Add a companion success/cost Pareto plot and two domains.

LoRA/QLoRA uses only the same training knowledge; budget training GPU-hours,
validation selection, update readiness, forgotten tasks and reversible
corrections. Architecture differences do not license different held-out answers.
Concurrency is measured at fixed GPU memory with separate sessions and the same
workload/SLA; logical live-process overlap is not throughput scaling.
